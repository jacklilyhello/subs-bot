# Private provider fetch runtime

`subs-bot-provider-fetch-dev-01` is a separate Worker with a single Container instance managed by a Durable Object. Its default Worker handler returns a fixed 404. The configuration disables workers.dev, previews, invocation logging and traces. The Container uses a nonroot Python process with no project credentials, data bindings or storage mounts. Direct Internet access allows public DNS and numeric dialing. The application checks every destination before it connects.

The private port exposes `GET /ready` and `POST /v1/fetch`. Fetch accepts only an `application/json` object containing `url`. The response body contains the downloaded bytes, with a SHA-256 header and optional bounded Base64URL metadata. Errors use fixed categories. Only one provider fetch can run at a time. The existing bot and subscription Worker have no binding to this service.

The hosted Provider Fetch CI job builds the Worker and the Linux amd64 OCI image, verifies the OCI manifest, config and layer digests, and checks that the tested image has the same config digest. It exercises the image without external networking and verifies the emitted Worker returns 404. The hosted artifact contains the exact Worker module, OCI archive and `provider-release.json` with the build ref, revision, run ID and attempt.

Run `gh workflow run worker-provider-artifact-preflight.yml --ref main -f provider_ci_run_id=<run-id>` against the successful Provider Fetch CI build of current `main`. The preflight checks the run, streams and verifies GitHub's archive, and verifies all three files in private runner storage. It uses only read access to GitHub. Earlier manifest versions are ineligible. For a later release, `release_artifact.py config` also requires the verified source run ID and attempt with `--run-id` and `--run-attempt`, and an explicitly supplied account ID.

## Authorized isolated deployment

Configure the GitHub environment `subs-bot-provider-isolation` to admit only the `main` branch before adding its `SUBS_BOT_CF_PROVIDER_ACCOUNT_ID` variable and dedicated `SUBS_BOT_CF_PROVIDER_CONTAINER_TOKEN` secret. Scope the token to the selected account with Workers Containers Write. The workflow requests short-lived Cloudflare Registry credentials with pull and, when necessary, push permission. Cloudflare issues those credentials at account scope. The workflow confines registry access to the fixed `subs-bot-provider-fetch-dev-01` repository. [Registry credentials API](https://developers.cloudflare.com/api/resources/containers/subresources/registries/subresources/credentials/methods/generate/) · [GitHub environment protection](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments#deployment-branches-and-tags)

Run `gh workflow run worker-provider-registry-publish.yml --ref main -f provider_ci_run_id=<run-id>` for the successful Provider Fetch CI build of current `main`. The workflow reuses the verified OCI archive and reads back the exact manifest and config by digest. It adopts an existing revision-and-digest tag only after verifying the full digests. Keep all writers for this repository under the protected workflow's concurrency group. The registry's OCI tag operation has no compare-and-set guarantee against an independent writer. A failed or interrupted job can leave the image in the registry. Rerun to verify and adopt it if both digests match. [OCI Distribution Specification](https://specs.opencontainers.org/distribution-spec/) · [Cloudflare image management](https://developers.cloudflare.com/containers/guides/image-management/)

Worker deployment is a separate operation. Deploy by digest to the fixed project name, with the account, Worker, Durable Object namespace, Container application and Workflow identities checked before writes and read back afterward. The first Worker creation requires Workers product Admin. [Workers roles](https://developers.cloudflare.com/workers/authorization/workers/)

The private Workflow `subs-bot-provider-fetch-dev-01-smoke` is triggered through Cloudflare’s authenticated Workflow API. Use instance ID `provider-smoke-<provider revision>` and parameters `providerRevision` and `isolatedRevision`. Verify the deployed Worker and image first. The smoke accepts one attempt per provider revision, starts one `lite` instance, and tests the existing isolated subscription Worker’s fixed `/health` using only validated Cloudflare edge addresses and no redirects. It also checks rejection of IPv4 loopback, IPv6 loopback and a link-local address, then destroys the instance. Require `ok: true` and an independent stopped-state readback. DNS family counts show which answers were approved. A separate test is required to establish IPv6 connectivity. [Workflow instance API](https://developers.cloudflare.com/api/resources/workflows/subresources/instances/) · [Container lifecycle](https://developers.cloudflare.com/containers/api/durable-object-container/)
