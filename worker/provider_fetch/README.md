# Private provider fetch runtime

`subs-bot-provider-fetch-dev-01` is a separate Worker with a single Container instance managed by a Durable Object. Its default Worker handler returns a fixed 404. The configuration disables workers.dev, previews, invocation logging and traces. The Container uses a nonroot Python process with no project credentials, data bindings or storage mounts. Direct Internet access allows public DNS and numeric dialing. The application checks every destination before it connects.

The private port exposes `GET /ready` and `POST /v1/fetch`. Fetch accepts only an `application/json` object containing `url`. The response body contains the downloaded bytes, with a SHA-256 header and optional bounded Base64URL metadata. Errors use fixed categories. Only one provider fetch can run at a time. The existing bot and subscription Worker have no binding to this service.

The private Container port also accepts `POST /v1/api-status` with exactly `url` and `key`. It uses the same public-address pinning and TLS checks for one HTTPS GET to a `/models` or `/chat/completions` path without a query or fragment. It sends the supplied key only to that origin, refuses redirects and returns HTTP status and elapsed milliseconds. The transport closes the upstream response after the headers and has a separate 15-second deadline.

The private `ProviderFetch` named entrypoint exposes `fetchSubscription({ url, providerRevision, imageSha256 })`. It verifies the expected revision and image before starting the singleton Container. The Container port receives only `{ url }`. A successful result contains an `ArrayBuffer` of at most 10 MiB and its verified SHA-256, plus optional validated `content-type`, `content-disposition`, `profile-title` and `subscription-userinfo` metadata. Failures return a fixed category, a retry hint and, for upstream HTTP failures, a validated numeric status. RPC calls follow the named service deployment and cannot request a Worker version override. [Named service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/#named-entrypoints) · [Version overrides](https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/#service-bindings)

The same private entrypoint exposes `probeApiStatus({ url, key, providerRevision, imageSha256 })` through the existing `ctx.exports.ProviderContainer` singleton. It shares the busy gate with subscription fetches and release smoke. After checking the revision and image, the controller posts only `{ url, key }` to the private port once, bounds the reply to 256 bytes and confirms Container shutdown. The result is either `{ ok: true, status, elapsedMs }` or `{ ok: false, code }`. The URL and key stay in the active call. A Telegram command would require separate application wiring.

`probeApiStatusV2` adds an integer `dispatchBeforeMs` in Unix epoch milliseconds, at most 30 seconds ahead. The caller must derive it from its authorized work deadline. The named entrypoint and singleton reject elapsed work before startup, and the controller rechecks before the sole `/v2/api-status` POST. The Container checks before DNS, after DNS, and at the TLS request writer, with a one-second guard and a bounded monotonic timeout. The absolute local dispatch cutoff depends on adverse clock skew and the final check-to-write delay together staying within that guard. Network delivery of an already dispatched request can occur later. V2 returns the same closed result as V1. Activating a caller of V2 requires a verified Provider Worker and image that implement it.

The subscription Worker's scheduled consumer requires `PROVIDER_FETCH`, `PROVIDER_REVISION` and `PROVIDER_IMAGE_SHA256`. Its release setup leaves them unset until a separately verified provider release is ready. Hosted tests connect a synthetic named entrypoint to the emitted Worker and exercise the existing import and refresh job records through D1, R2 and HTTP export. The Cloudflare egress smoke and real provider compatibility checks remain separate.

The hosted Provider Fetch CI job builds the Worker and the Linux amd64 OCI image, verifies the OCI manifest, config and layer digests, and checks that the tested image has the same config digest. It exercises the image without external networking and verifies the emitted Worker returns 404. Before upload, CI uses the publication workflow's pinned Skopeo to copy the exact archive to a local OCI layout and compares its raw manifest and config digests. The copy and inspection run in an isolated network namespace. The hosted artifact contains the exact Worker module, OCI archive and `provider-release.json` with the build ref, revision, run ID and attempt.

### Separate API status build profile

The hosted `api-status-runtime` job builds `subs-bot-provider-api-status-v2-<revision>-<run-attempt>` for the fixed private service and OCI repository `subs-bot-provider-api-status-dev-01`. Its version 3 manifest requires the `api-status-v2` profile, the `ProviderApiStatus` entrypoint and an image config with the matching `io.subs-bot.provider.profile` label. The named service exposes only `probeApiStatusV2` and uses its own `provider-api-status-v2` singleton name. It requires the V2 image repository and the caller's digest before startup.

The default subscription artifact still uses manifest version 2 and the original service. Existing protected deployment and recovery workflows accept only that profile. Provisioning the V2 Worker, verifying live V2 egress and adding its independent application binding are separate release steps.

## Approved hosted source samples

`worker-provider-live-samples.yml` runs manually from current `main` in the protected `subs-bot-provider-isolation` environment. The default `transport` mode accepts 1 to 12 distinct, approved original URLs. Use the dedicated one-time environment secret `SUBS_BOT_PROVIDER_LIVE_SAMPLE_JSON` for a privately prepared JSON object with `version` set to `1`, one HTTPS `origin`, one exact `path`, and an ordered `urls` array. Supply the independently computed SHA-256 of the exact manifest bytes as `sample_manifest_sha256`. Keep the manifest in the secret and use only its SHA-256 in the dispatch input. The manifest must fit 48 KiB. The protected run checks that the transport would preserve each URL's original spelling and that every URL matches the approved origin and path, has a query and has no fragment. [GitHub environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)

The GitHub-hosted runner installs the pinned wheels before the sample secret is exposed. It uses one application attempt per URL, serially, with a one-second pause between attempts and redirects disabled. The transport applies pinned DNS, socket and TLS checks, a 25-second deadline per URL, and separate 10 MiB limits on wire and decoded body bytes. The batch has a 330-second deadline. HTTP `429` stops further samples. The workflow refuses run retries. The operator retires the one-time secret after reviewing the run. The report contains only case numbers, fixed outcomes, decoded byte counts and numeric upstream failure status where available. A successful workflow run means the report completed, which can include per-URL failures. Response bytes and bounded parser metadata stay in an owner-only runner directory that the sampling step removes. The workflow has no artifact upload or cache.

For `mode=compare`, use a separately approved manifest of at most four URLs and supply `worker_ci_run_id` from successful Worker CI on the same current `main` revision. The job verifies that artifact, installs locked Node 24 dependencies and prepares a separate Python 3.11 environment plus checksum-pinned Mihomo and Sing-box before receiving the sample secret. The same step feeds each successful capture to the legacy parser and replays it through the emitted Worker with synthetic bindings. It reports job, snapshot and HTTP export outcomes plus native client checks where applicable. The native validators run with networking disabled. Sampling and comparison share one owner-only scratch directory that is removed when the step exits.

A completed comparison with at least one saved replay exits `0`. A completed comparison with zero saved replays still prints its report and exits `1`. A manifest, integrity or runner failure exits `2`. These runs measure GitHub-hosted egress and hosted Workerd replay. Cloudflare Container egress, the live named service binding and live D1/R2 publication are separate checks.

Run `gh workflow run worker-provider-artifact-preflight.yml --ref main -f provider_ci_run_id=<run-id>` against the successful Provider Fetch CI build of current `main`. The preflight checks the run, streams and verifies GitHub's archive, and verifies all three files in private runner storage. It uses only read access to GitHub. Earlier manifest versions are ineligible. For a later release, `release_artifact.py config` also requires the verified source run ID and attempt with `--run-id` and `--run-attempt`, and an explicitly supplied account ID.

### Provider binding proof

The protected activation workflow publishes `subs-bot-provider-binding-proof-<workflow-revision>-<run-attempt>` only after `smoke` completes or read-only `verify` confirms the same completed smoke. The final checks include public denial, independent Container shutdown, and exact provider resource and `main` readback. The artifact contains one canonical `provider-binding-proof.json`. It records the verified Provider Fetch CI artifact and module/OCI digests, the activation run and attempt, isolated health revision and digest, and fingerprints for the observed account, Worker, version, activation, Container, Workflow and actor. Version 1 uses the same workflow and Provider revision. Version 2 authenticates both revisions separately for the pinned historical continuation. The artifact expires after 30 days. A verification dispatch can produce fresh evidence for an admitted release without another smoke mutation.

A future binding workflow must select the exact successful `workflow_dispatch` run of `worker-provider-isolation-activate.yml` from this repository's `main`, match the workflow identity, commit and attempt, and verify GitHub's artifact archive SHA-256. Require one bounded regular manifest in the archive and validate it against the authenticated run metadata. Compare the proof with protected identity pins and fresh Cloudflare readback of the provider account, immutable Worker, private settings, active deployment, version, module, OCI digest and Durable Object namespace before activating a caller. The proof covers the fixed isolated health smoke and records the private provider state at verification time. This workflow publishes evidence only.
