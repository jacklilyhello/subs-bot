# Cloudflare 生产切换执行方案

本文件是执行顺序与批准清单，不是生产切换完成记录。生产批准必须指向一份已封存、没有必填空项的目标清单及证据索引；不能只批准某个分支、候选包名称或 `productionReady` 值。

本轮只准备和演练。不得改变正式 Bot、Webhook、正式域名、旧消费者或生产数据库。已有隔离 Worker `subs-bot-cf-dev-01`、`@test_cfsubs_bot`、两个获准账号和指定测试群仍是测试边界。恢复目标保持私有且没有 Telegram 消费者。短链服务只允许经现有 `shortlink-new` / `ShortlinkService` 业务绑定调用，不变更该服务。

## 批准前固定目标

以下值在受保护清单中逐项固定。公开 PR 只放适当的资源名称、摘要、数量、提交和运行指针；Bot Token、Webhook Secret、能力链接、数据库内容、用户清单及完整配置不能进入公开产物。清单摘要应与最终批准一起保存。

| 项目 | 必须核对的值 | 未确认时的处理 |
| --- | --- | --- |
| 源实例 | 维护者、主机/服务归属、部署提交、启动方式、systemd 单元及 InvocationID、真实 `DB_PATH`、其他写入进程 | 不猜测 `/opt/subs-bot` 模板就是生产位置，不连接未知主机 |
| 源 Bot | `getMe` 的 Bot ID/用户名、当前 Webhook 模式、实际轮询进程数、受控凭据来源 | 不用测试 Bot 代替正式 Bot，不启动第二个 `getUpdates` 消费者 |
| 源数据和旧链接 | SQLite 一致备份、配置摘要、旧公开 origin/路径、短链域名及归属、有效能力种类、群级数据归属 | 未知来源或归属列为阻塞，不以空库或重发链接替代 |
| 目标代码 | 完整 main SHA、CI run/attempt、产物/模块摘要、迁移顺序及摘要、已验证兼容恢复版本 | 不能只看绿色 CI 或相似二进制 |
| 目标资源 | Cloudflare 账户/Zone、生产 Worker/D1/R2 的唯一身份及创建记录、依赖版本、私有桶策略 | 隔离资源不是默认生产目标；无关资源不采用、不修改 |
| 正式入口 | 预留 `subs-bot.lilyya.top` 的 DNS/路由/Custom Domain 当前状态，以及需要保留的旧主机名 | 冲突或旧链接仍依赖其他主机名时停止绑定 |
| 接收与权限 | 正式 Bot、管理员/白名单/显式拒绝的来源摘要、通用授权世代、Webhook allowed_updates/连接上限、显示时区 | 默认 UTC；仅恢复实际持久设置，不改为默认新加坡时间 |
| 备份和恢复 | 私有持久位置、备份代、D1 SQL/数据摘要、R2 闭包清单、恢复目标身份、验证结果、保留期限及访问人 | 不能仅给短期 Actions 产物或签名下载 URL |

正式生产资源、正式 Bot 和旧消费者的位置必须由获准来源确认。本仓库的 service 文件与 `.env.example` 只说明部署约定，不证明这些生产实例存在或不存在。

| `legacy_inventory.py` 及各 `legacy_*_inventory.py` | 读取已封存且没有 sidecar 的 SQLite 备份，测量容量、分类旧域和能力 | 从运行中的 SQLite 主文件直接取得完整 WAL 数据 |

| `worker-isolation-native-restore.yml` | 按固定 cohort 捕获安静隔离源、封存 D1/R2、恢复到专用未绑定目标并逐项对账 | 通用生产备份/恢复；它的身份和空闲检查不能改为任意生产资源 |
| `worker-isolation-general-window.yml` | 固定测试 Bot 的 `inspect → close → drain → restore`，分类读回工作与终态 | 正式 Bot 的全局暂停/生产授权工具，或取消未完成工作 |
| `legacy_handoff.py`，经 `bot.py` 显式启用 | 私有 sidecar 持久记录每次轮询 offset、返回 ID 摘要、逐条 dispatch 状态和分类关闭摘要 | 启用前的历史、业务效果成功、消息恰好一次、丢失正文的回放，或去重边界已导入 D1 |
| 旧 `bot.py` 的 `SIGTERM` 关闭顺序 | 先停轮询，再等待应用，关闭 HTTP、SQLite 和上游会话，记录进程关闭结果 | Telegram 逐条业务成功、最后确认 offset、无损重放或全部外部发送成功 |

生产接管、生产暂停以及水位导入不能把隔离工具改个资源名后直接执行。必须在批准前审查确实适配正式 Bot、目标身份、前态摘要和暂停栅栏的执行工具，并在隔离环境证明其行为。未具备的步骤保持阻塞。

所有安装、构建、自动化测试、恢复和运行验收使用 GitHub 托管 runner 或 Cloudflare；本机只阅读、编辑、Git 操作及查看云端结果。源备份如需在旧主机执行，由已授权的数据拥有者采用已审查的备份步骤产生，不能借自托管 runner 在本机验证。

### 旧轮询的可选交接观测

`TELEGRAM_HANDOFF_LEDGER_PATH` 未设置时，旧服务保持原有启动行为。显式启用时同时要求：

```text
TELEGRAM_HANDOFF_LEDGER_PATH=<本项目私有目录内独立的绝对文件路径>
TELEGRAM_HANDOFF_REVISION=<维护者核对过的旧部署完整40位提交>
TELEGRAM_PRESERVE_PENDING_UPDATES=1
```

目录必须由运行用户拥有且权限为 0700；新账本为 0600，拒绝符号链接、其他应用数据库、不同 Bot 账本和协作进程同时打开。账本使用独立 SQLite、DELETE journal 与 FULL 同步提交，不改订阅数据库 schema。Bot ID 在初始化时与真实 `getMe` 核对；revision 是操作员固定的部署声明，仍须与实际部署文件独立核对。systemd 的 `INVOCATION_ID` 与每次独立 run 关联。账本 I/O 失败触发停止事件并阻止下一次受观测的网络拉取和 handler 调度，已开始的业务仍按关闭流程等待。保留最后已提交记录，不降级成未记录运行。

轮询调用开始先持久记录；只有收到成功响应并封存返回 ID 后才让 PTB 处理。成功调用的正 offset 证明其之前更新的 Telegram 确认边界，不证明 handler 已完成；网络失败/取消记录结果不明。`handler-returned` 仅表示当前阻塞 handler 返回，不证明业务或发送成功；框架捕获的 handler error、取消和重复 dispatch 单独累计保留，不因后续重试返回而消除。本适配器拒绝 `block=False` handler，后台外部效果仍须业务对账。

PTB 21.10 停轮询时还会以最后 offset 调用一次 `getUpdates`；该响应可能含未进入应用队列的新更新。因此账本分别统计 `fetchedNotStarted` 与其中 ID 已小于成功确认 offset 的 `fetchedNotStartedConfirmed`，不能把前者都认定为丢失，也不能忽略后者。停止后封存整个 sidecar 和它的逐次 run 记录，不能只保留最后一个最大 ID。`legacy-handoff:v1` 日志投影只含摘要/计数，精确 offset 保存在私有账本；`lifecycleComplete` 与原 drain 标记都只证明关闭流程结果。此能力不自动去重或回放，也不生成已验收的 D1 边界导入。启用前的观察空白、旧崩溃和已确认但未处理的更新仍是阻塞项。

本轮只交付观测实现和合成测试，不在旧生产实例启用它；启用需另行批准旧服务的部署/配置变更及必要启动窗口。启用后也不得调用负 offset 或清除待处理更新。

## 一致备份与真实数据演练

1. 先确认源访问授权、真实数据库位置、SQLite 版本和写入者。在线演练备份不停止旧服务、不修改其配置。采用 SQLite Online Backup API 或等价 `.backup`，通过 SQLite 连接读取包含已提交 WAL 的一致视图；不以文件系统 `cp subs.db`、`immutable=1` 读取活库或仅复制主文件作为在线备份。
2. 将备份写入新的私有文件。仅对备份目标关闭连接、转为 DELETE journal mode、确认没有 `-wal`、`-shm`、`-journal`，再执行完整性/外键检查并封存摘要、大小、起止时间、源部署/配置摘要和备份方法。不能对活库执行破坏性清理来迎合导入工具。备份失败、仍在变化或有 sidecar 时不交给要求 immutable 输入的 inventory/converter。
3. 从同一备份代生成容量和各域 inventory。至少核对活动订阅、回收站、用户归属、路径规则、临时节点、显式授权、管理员/初始白名单、私密分享/领取、普通和格式短链、选定/动态聚合及实际存在的相关状态。记录不支持域、无效记录和超限记录，任一非空域没有明确承接方案即停止完整导入。
4. 固定所有权映射和旧 origin；群级旧归属不明时让维护者决定，不自动归给管理员或两个测试账号。旧 code/token、撤销墓碑、过期规则、份数、已领取用户、关联对象和序列高水位都进入核对。授权比较包含实际配置与数据库覆盖项，不能只比较 `auth_overrides` 数量。
5. 导入到专用私有恢复 D1/R2，不绑定测试 Bot、正式 Bot、Webhook、Cron、队列消费者或公开域名。真实数据不装入现有两账号交互环境。仅通过获准的受保护验证入口/受控云端任务检查；报告只含分类计数和摘要。
6. 比较逐域数量、按所有者和关联关系生成的摘要、迁移 ledger、序列、外键及全量元数据摘要。逐个核对引用的 R2 清单、块、字节、摘要和必要元数据；验证有效旧链接的解析和完整输出、过期/撤销/越权拒绝及领取连续性。能力本身不输出到日志或公开报告。
7. 封存源备份、转换输入/输出清单、目标 identity、对账结果和恢复 checkpoint。演练状态标为真实备份或合成夹具；合成通过不能填补真实来源的 Not run。

在线备份只是演练基线。旧服务持续写入时它不能替代切换窗口的最终快照；本方案不假定已有完整 SQLite 增量复制器。

## 单消费者交接的执行顺序

以下步骤只在目标、备份、恢复、权限和链接门槛通过，并取得逐项生产授权后执行。保持旧消费者接收期间，新入口始终关闭；停止旧消费者后，新入口也保持关闭直到最终对账完成。

1. **窗口前只读核对。** 固定源/目标身份、准确提交、当前 Webhook、旧实例启动记录、自动重启/定时启动来源及旧 HTTP 写入口。记录 Telegram 待处理数量和错误时间，但不能把 `pending_update_count=0` 当成没有已取走工作。不得用额外轮询探测器抢走或确认更新。
2. **关闭旧侧新增写入口。** 在已批准的维护窗口阻止旧 HTTP 管理/领取及其他写入口继续产生数据；停止旧 Telegram 拉取。执行实际部署版本支持的优雅停止，核对指定 InvocationID 内的关闭结果，并确认进程退出、无人自动重启。只读导出是否保留须由实际旧拓扑决定。不得直接 kill 后声称排空。
3. **封存最后处理边界。** 保存最后成功 `getUpdates` 请求 offset、返回/已确认更新区间、已处理 update_id 集合及摘要、未开始/执行中/失败/结果不明记录，并关联同一 Bot、进程实例和快照。最大 update_id 和消息时间不能代替精确边界；乱序和空洞必须逐条分类。旧版本没有此证据时停止，先完成受审查的窗口观测/交接能力，不能猜测水位。
4. **分类排空。** 所有已受理工作逐类核对，见下表。明确失败和外部发送不确定单独保留；等待本身不能将其改为成功。继续工作仍有可执行租约时不生成最终快照。不得删除记录、清空队列或重发不确定的消息来制造零计数。
5. **最终一致快照。** 确认所有旧写入者都已停止，在同一停写边界取得 SQLite 一致备份、配置/权限摘要和最后水位。再次确认数据库无后续变化。与演练基线做逐域新增/更新/删除核对；没有验收过的增量器时，从最终完整备份重新生成候选并导入新的未绑定生产目标，不能将差异凭人工猜测补齐。
6. **最终独立对账。** 对目标重新检查全部域、归属/授权、对象闭包、旧链接和序列，核对迁移 ledger、资源身份、候选模块/依赖、UTC/持久时区。将旧已处理更新的去重边界与新 D1 收件模型衔接并验证；没有验证过的边界导入工具时保持新入口关闭。不得用设置 `cutoverAt=now` 丢弃早于该时间但尚待处理的更新。
7. **先准备目标，再接管入口。** 将准确候选部署到生产 Worker，保持接收/后台写入暂停并独立读回 100% 版本、D1/R2 绑定和恢复控制。正式域名及所有仍有效旧 origin/路径按批准清单接入。只有旧消费者确认停止、最终数据核对通过后，才为准确正式 Bot 设置唯一 Webhook。显式 `drop_pending_updates: false`，保留原本需要的 update 类型、密钥和连接参数，读回 `getWebhookInfo`。设置请求结果不明时只核对，不能切换到另一个消费者试探。
8. **打开新接收并验收。** 按固定生产授权世代打开接收；持久化成功才返回 2xx，暂不能受理返回可重试状态。Webhook、Cron 和其他写入者使用同一数据库及同一接收栅栏。核对最早新 receipt、水位/重复更新、角色权限、旧链接、写入读回、后台任务和错误计数。真人验证的范围须包含在生产授权中，不能把现有测试账号授权扩大到正式用户。
9. **结束窗口。** 将最终版本、接收起点、已受理/已终止/不确定计数和 D1/R2 checkpoint 封存。旧消费者继续停用并保留数据，不自动启动。观察期、备份保留期和旧入口退役日期由批准清单固定，过期也不自动删库或撤掉有效旧链接。

### 已受理工作的分类

| 类别 | 排空/保留要求 |
| --- | --- |
| 旧轮询已取走但未进入 handler | 必须有逐条交接/回放计划；不能依赖 Telegram 必然重投 |
| 正在执行的旧 handler、上传、拉取、批量刷新、API 探测 | 等待落定；取消/超时列为失败或不确定；同时核对数据与回复效果 |
| 旧进程内对话、临时节点输入和待提交选择 | 明确哪些已有持久状态可迁移；未持久状态需提示重新开始，不能当已提交业务数据丢弃 |
| D1 inbox/outbox、普通及旧通用回复 | 待发送/租约/重试全部核对；每个成功发送保留 message_id，网络结果不明不自动重发 |
| 文档任务/暂存、提供方单条/文档/批量及结果回复 | 既检查 visible outbox，也检查尚未产生 outbox 的未来生产者 |
| 私密创建、群卡、内联、快照租约、搜索、探测 | 租约及仍可发送/编辑的工作阻塞排空；终态失败/不确定单独封存 |
| 普通/格式短链签发与撤销 | 核对本地稳定 code、外层签发尝试/终态、撤销墓碑；禁止绕过 Service Binding 重试 |

现有隔离控制器的 16 项 `work` 和 `terminalCards` 可作为生产工具设计的参考。生产工具仍须核对正式 Bot 的完整作用域；不能直接复用固定两账号的世代或把全库任务误判成无关任务后忽略。

### 重复更新、积压和旧回调

- 目标以 `(bot_id, update_id)` 持久去重，已持久化重复投递不得再次执行业务。旧实例已处理集合必须与其快照对应；仅导入订阅而没有去重边界，会留下跨消费者重复执行风险。
- Telegram 尚未交给旧消费者的更新保留原队列，按明确的接管边界进入新收件箱。不得调用 `drop_pending_updates: true`，也不得用一个高 offset 的临时 `getUpdates` 消除积压。
- 新旧 handler 语义不同的旧按钮、私密领取、内联和文档回调须按真实格式验证。能证明身份/所有权和对象状态才执行；不支持的按钮明确失效并提示重新发命令，不能转成另一项写操作。已完成的领取和撤销状态继续生效。
- Telegram 发消息没有通用业务幂等键。响应超时、成功回复后落库失败和进程崩溃的交界只能封存为不确定并人工核对，不能承诺所有外部效果恰好一次。

## Cloudflare 已接收新写入后的失败恢复

**先停止新增写入并保留现场。** 关闭新 admission 与管理/领取等可写入口，保留正在完成的工作所需依赖，固定已受理水位并分类排空。若不能证明栅栏阻止所有生产者，保持服务暂停，不实施覆盖式数据恢复。停止 Cron/队列前先核对是否会遗弃可完成工作；有不确定外部效果时不自动回放。

**仅恢复代码时，保留当前数据。** 兼容版本必须逐项证明支持当前所有迁移、授权世代、回执/租约、能力和撤销语义、已启用的 provider/短链/临时节点/分享格式及配置。记录准确模块摘要和版本 ID，完成独立读回。`5752d09` 是交接时的历史候选，不因曾运行成功就成为任意未来 schema 的兼容版本。平台拒绝旧 Secret 版本时，只有经审查的相同模块/绑定/原凭据向前发布恢复可用；不得强制忽略身份或 Secret 核对。

**必须恢复数据时，使用独立目标。** 封存暂停后的现状 G1：D1 全量导出/书签、完整 R2 引用闭包、所有收件/回复/任务状态、配置和目标身份。选择历史备份 G0，在新的私有且无消费者的 D1/R2 还原并完整对账。原 G1 不覆盖、不删除；D1 Time Travel 不能恢复 R2，也不构成整套恢复。

G0 之后的新增、更新、删除、授权、领取/份数、撤销、短链、回复及回调都必须从 G1 单独对账。当前不假定存在经过验证的完整 G0→G1 增量回放器；不得把 SQL 导出差异直接重放到另一 schema，也不能只搬新增行忽略更新/删除与外部效果。若不能完整保留 G1，保持停写，提交明确的数据处置决定及影响，由维护者另行批准。完成独立恢复验证后，才可申请切换数据绑定。

**旧 SQLite 不自动接回。** 它没有 Cloudflare 已接收的新写入。只有完整反向迁移/增量回放经过实现、演练、归属/链接/去重核对，或维护者明确批准了具体数据处置，才能计划回到 SQLite。届时须先停新消费者和确认 Webhook，再以 `TELEGRAM_PRESERVE_PENDING_UPDATES=1` 启动唯一旧轮询。启动旧轮询会移除 Webhook；保留 Telegram 队列不能补回 Cloudflare 已经确认的更新。

## 立即停止条件

下列任一条件出现，停止下一项写操作，保留所有原件、checkpoint 和不确定操作记录，只做独立读回；不要以重复 mutation、强制部署、清队列或空库替代：

- 来源授权/身份不明，发现额外消费者、写入者、域名冲突、外部服务归属不符或跨项目资源。
- 备份变化、WAL 一致性未证实、任一非空域未承接、所有权/授权/对象/旧链接对账不一致。
- 旧消费者无法优雅停止、被自动重启、最后处理边界不明、待处理更新存在无归属空洞。
- 已受理工作仍有有效租约或未来生产者；失败/结果不明尚无明确处置；新旧消费者可能同时写不同数据库。
- CI/部署 attempt、实际模块/配置/绑定/迁移或快照摘要与批准不符；工具要求绕过安全检查才能继续。
- API mutation 响应不确定、创建资源未固定身份、恢复导入/对象检查失败、恢复目标出现消费者或公开访问。
- Cloudflare 已产生新写入但恢复方案不能保留它们，或需要超出批准范围的数据/权限/费用决定。

## 最终请求批准的具体生产操作

最终批准请求应附完整目标清单摘要、准确代码/CI/隔离部署和数据恢复证据，并逐项列出以下变更。存在真实来源、生产身份或水位工具缺口时，先请求最少必要信息；此时只能审查方案，不能执行生产切换。

1. 确认唯一旧实例/消费者及正式 Bot；批准维护窗口、关闭旧写入口、优雅停止和禁止自动重启。
2. 批准取得最终一致备份和封存最后更新边界；保留原始 SQLite、配置和历史链接，不覆盖原件。
3. 批准创建/采用清单中的唯一生产 Worker、私有 D1/R2 及最小必要依赖，导入已对账的最终候选；不得以空库上线。
4. 批准准确候选版本、通用授权世代与正式入口开关，以及预留域名和确有需要的旧链接入口绑定；列出每项配置差异。
5. 批准对准确正式 Bot 设置唯一 Webhook，明确 `drop_pending_updates: false`、接收集合和水位衔接；执行后独立读回。
6. 批准限定的生产验收动作、通过标准、观察窗口、失败停写控制和备份保留期。任何数据恢复/反向迁移仍需指向具体 G0/G1 和保留方案，不能由“演练成功”自动授权。

所有批准完成前，隔离测试继续与正式生产分离，通用生产入口保持未启用。
