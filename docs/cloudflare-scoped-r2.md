# Bucket-scoped R2 object transport

The lifecycle and private evidence stores can use separately scoped S3 object credentials while continuing to verify bucket identity, public-domain settings and lifecycle rules through the Cloudflare metadata API. This option is disabled when both `SUBS_BOT_SCOPED_R2_READ_JSON` and `SUBS_BOT_SCOPED_R2_WRITE_JSON` are absent; the existing transport remains the default. Set `SUBS_BOT_CF_R2_METADATA_READ_TOKEN` separately for the metadata API. That token is never used as the S3 object credential.

The two S3 settings are protected Environment Secrets containing JSON maps from the exact bucket name to an object with `accessKeyId` and `secretAccessKey`. Each entry must correspond to an independently verified Cloudflare token limited to that bucket: Object Read only for the read setting, and Object Read & Write for the write setting. A read-only job omits the write setting. When either setting is supplied, the exact selected bucket must have a read entry; a missing, malformed or differently scoped entry stops the operation rather than falling back to REST. Credential format, bucket names and client-side path checks are not evidence of the platform token policy; independently inspect and record the actual policy and expiration before injection.

Object reads and immutable conditional writes use S3 Signature V4. A new object is created once with `If-None-Match: *` and independently read back; a conflict or an unconfirmed response is not retried. The S3 primitive also supports exact ETag `If-Match` coordination and complete, bounded ListObjectsV2 pagination. Existing callers that use a separate journal or one-shot intent must explicitly integrate these primitives before they can use this transport; setting credentials alone does not establish that their workflow has been converted.

Native and production recovery use the scoped transport for referenced-object and checkpoint reads/writes when configured. S3 listings are followed by HEAD requests for referenced business objects; metadata, size and ETag are checked together, and supported HTTP and custom metadata are retained on restore. The trusted isolation cleanup also uses the scoped transport for its complete anchor inventory and exclusive intent. Exact equivalence between the S3 HEAD metadata representation and the previous REST listing, including an absent or implicit Content-Type, expiry, custom metadata, storage class and ETag, still requires isolated live verification; uncertain or inconsistent results must stop the operation.

This transport does not create or activate resources, alter bucket settings, grant approval for a maintenance action, or verify a credential's platform scope. Backup orchestration and Provider archive inventory additions in other branches require their own integration and exact-head isolated validation before use.
