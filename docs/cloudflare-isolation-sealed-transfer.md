# Sealed transfer of fixed isolation configuration

`worker-isolation-sealed-transfer.yml` supports only the fixed test-project mappings in `isolation_sealed_transfer.py`. It cannot copy an arbitrary secret, Cloudflare token, management credential, or production configuration. The `seal` jobs are disabled unless `SUBS_BOT_SEALED_TRANSFER_ENABLED` is `true`; the read-only `plan` job does not access secrets.

The operator must independently retrieve the exact destination Environment ID, public key and key ID through the authenticated GitHub API, then dispatch `plan` from current `main` with those public values and the selected fixed mapping. Before sealing, independently compare the planned destination and key data with those API responses and set the corresponding protected source-Environment key-pin variable returned by the plan. A plan alone does not authenticate a caller-supplied public key. The source job rechecks the fixed source, destination, mapping, public-key pin and current main before it reads its selected configuration.

Before sealing, independently list each required source Environment's Secret names and update timestamps, its immutable Environment ID and branch policy, and all repository-level Secret names. Verify that all selected names exist in the fixed source Environment, that no same-named repository fallback can supply a missing value, and that the source Environment permits only `main`. Record the exact metadata in the versioned `source_metadata_json` schema enforced by `operator_source_metadata`, pin its canonical SHA-256 and source Environment ID in protected source-Environment variables, and use it within 30 minutes. The default GitHub Actions token used here cannot independently list that administrative metadata; the metadata pin is an operator attestation, not an automatic live GitHub check. Re-read and compare the same metadata immediately before the destination PUT; any change or uncertainty requires a new attestation.

The isolation source step reads Worker metadata using `SUBS_BOT_SEALED_WORKER_READ_TOKEN`, and reads the fixed registration object through S3 using `SUBS_BOT_SEALED_R2_ACCESS_KEY_ID` and `SUBS_BOT_SEALED_R2_SECRET_ACCESS_KEY`. Before injection independently verify the Worker token is Metadata Read-Only for the one original test Worker, and the S3 key is Object Read only for the one original test bucket, with suitable expiration. A successful request and a credential name do not prove scope. Bucket-scoped R2 object credentials do not support the Cloudflare REST object API; S3 object access alone does not establish bucket creation time or privacy settings.

There is no runner-side live D1 or bucket-configuration read in this workflow. Immediately before sealing, an operator must use an existing authorized read-only channel to inspect only the exact original test Worker, D1 and bucket identities, bucket privacy and lifecycle policy, then put a canonical `SUBS_BOT_SEALED_SOURCE_EVIDENCE_JSON` in the protected source Environment. Its exact fields are `version: 1`, `checkedAt` (UTC Unix seconds), `sourceTarget` (the complete independently observed original target, including account, Worker and D1 IDs and creation times, bucket creation time and namespace), `databaseName`, `bucketName`, `bucketJurisdiction: "default"`, `bucketPublicAccessDisabled: true`, `bucketDeletionRulesDisabled: true`, and `registrationSha256`. Both names must be `subs-bot-cf-dev-01`; the boolean observations require the managed public domain disabled, no custom domains and no enabled object-deletion lifecycle rule. Independently pin the canonical SHA-256 as `SUBS_BOT_SEALED_SOURCE_EVIDENCE_SHA256`; the observation expires after 30 minutes. Construct the evidence from independent observed identities and prior trusted registration, never by hashing the unverified value being transferred. The workflow compares the full source target to this pin, but this is an operator attestation, not an independent live D1 or bucket-privacy verification. The GitHub metadata attestation must include the source evidence and both scoped credentials as Environment Secrets without repository fallbacks.

The pinned registration also binds the target and signing-key digests; the test Bot identity is checked live. The Provider source step requires a target digest independently obtained from previously verified Provider target evidence and protected in the source Environment; deriving that pin from the value being transferred is not independent verification. A second step in the same trusted-main job repeats the source checks and seals only a source value whose digest matches the first check. Missing or uncertain metadata, token scope, registration, keys or Bot identity stops the transfer. No read credential is exported by these mappings.

These checks only permit creation of ciphertext for review. Before any isolated resource mutation or operation requiring a live identity, use compliant project-scoped credentials to independently verify the actual resource identity and required privacy/dependency state. If a single-database D1 permission is not established or any required live state cannot be verified, stop that operation; the operator observation does not replace it.

Only the GitHub-compatible `encrypted_value` and `key_id` are uploaded. The source runner never receives a GitHub personal access token, and the workflow never writes a destination secret. A separate authorized caller must verify the exact successful trusted-main run, selected mapping, artifact digest and reported key pin; independently re-read the same destination public key and key ID immediately before submitting the ciphertext to the fixed destination secret endpoint. Stop on a changed key or an unknown write result. Do not submit plaintext, export a management credential, or automatically retry an unconfirmed write.

GitHub does not return stored secret values. A successful write response alone is therefore not verification of the target configuration or token permissions. Use a separately protected, read-only destination check for the exact test resource identities and applicable permissions before any isolated operation. These mappings do not grant production activation, webhook switching, deployment or consumer-switch authority.
