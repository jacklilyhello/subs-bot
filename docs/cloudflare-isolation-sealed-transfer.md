# Sealed transfer of fixed isolation configuration

`worker-isolation-sealed-transfer.yml` supports only the fixed test-project mappings in `isolation_sealed_transfer.py`. It cannot copy an arbitrary secret, Cloudflare token, management credential, or production configuration. The `seal` jobs are disabled unless `SUBS_BOT_SEALED_TRANSFER_ENABLED` is `true`; the read-only `plan` job does not access secrets.

The operator must independently retrieve the exact destination Environment ID, public key and key ID through the authenticated GitHub API, then dispatch `plan` from current `main` with those public values and the selected fixed mapping. Before sealing, independently compare the planned destination and key data with those API responses and set the corresponding protected source-Environment key-pin variable returned by the plan. A plan alone does not authenticate a caller-supplied public key. The source job rechecks the fixed source, destination, mapping, public-key pin and current main before it reads its selected configuration.

Before sealing, independently list each required source Environment's Secret names and update timestamps, its immutable Environment ID and branch policy, and all repository-level Secret names. Verify that all selected names exist in the fixed source Environment, that no same-named repository fallback can supply a missing value, and that the source Environment permits only `main`. Record the exact metadata in the versioned `source_metadata_json` schema enforced by `operator_source_metadata`, pin its canonical SHA-256 and source Environment ID in protected source-Environment variables, and use it within 30 minutes. The default GitHub Actions token used here cannot independently list that administrative metadata; the metadata pin is an operator attestation, not an automatic live GitHub check. Re-read and compare the same metadata immediately before the destination PUT; any change or uncertainty requires a new attestation.

The isolation source step also uses a separately supplied credential to verify the exact original Worker and D1 identities and independently pinned private registration; it checks the registered target, signing-key digests and live test Bot identity. Before providing `SUBS_BOT_CF_SEALED_SOURCE_READ_TOKEN`, independently establish that its actual scope and expiration permit only the necessary project-scoped Worker, D1 and R2 reads; its name and successful GET requests do not establish its permissions. The Provider source step requires a target digest independently obtained from previously verified Provider target evidence and protected in the source Environment; deriving that pin from the value being transferred is not independent verification. A second step in the same trusted-main job repeats the source checks and seals only a source value whose digest matches the first check. Missing or uncertain metadata, token scope, registration, keys or Bot identity stops the transfer. No read credential is exported by these mappings.

Only the GitHub-compatible `encrypted_value` and `key_id` are uploaded. The source runner never receives a GitHub personal access token, and the workflow never writes a destination secret. A separate authorized caller must verify the exact successful trusted-main run, selected mapping, artifact digest and reported key pin; independently re-read the same destination public key and key ID immediately before submitting the ciphertext to the fixed destination secret endpoint. Stop on a changed key or an unknown write result. Do not submit plaintext, export a management credential, or automatically retry an unconfirmed write.

GitHub does not return stored secret values. A successful write response alone is therefore not verification of the target configuration or token permissions. Use a separately protected, read-only destination check for the exact test resource identities and applicable permissions before any isolated operation. These mappings do not grant production activation, webhook switching, deployment or consumer-switch authority.
